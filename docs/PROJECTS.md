# Карта проектов

## Зачем разделять

Система состоит из трёх самостоятельных частей. Их нужно документировать и обновлять независимо, сохраняя согласованный контракт между ними.

| Компонент | Ответственность | Что не должен делать |
|---|---|---|
| FR24 Collector | Получать LiveFeed, декодировать protobuf, обновлять общий кеш | Не знать модель и экран конкретного ESP32 |
| HTTP API / Area Manager | Принимать координаты, собирать и объединять зоны, фильтровать ответы | Не декодировать данные на ESP32 |
| ESP32 Firmware | Показывать радар, часы и настройки; опрашивать сервер | Не обращаться напрямую к FR24 и не хранить HAR |

## Предлагаемая структура репозиториев

На текущем этапе код сервера остаётся в этом репозитории, а прошивка — в отдельном репозитории Flight Radar-D & Clock. Не переносите файлы прошивки в серверный репозиторий.

- `FR24_Standard_API` — сервер, коллектор, API, документация и серверные тесты.
- `flight-radar-d-clock` — прошивка ESP32, дисплей, настройки радара и сетевой клиент.
- При необходимости позже: `FR24_Operations` — отдельные скрипты установки, резервного копирования и мониторинга. Создавать его сейчас не требуется.

## Контракт между сервером и ESP32

Прошивка отправляет HTTP GET:

```text
/v2/lat/{latitude}/lon/{longitude}/dist/{distance_nm}
```

Сервер отвечает JSON с полями `ac`, `msg`, `now`, `total`, `ctime`, `ptime`. Этот маршрут и основные поля ответа сохраняются для совместимости.

## Правило изменений

1. Изменения прошивки — только в репозитории прошивки.
2. Изменения FR24-декодера, кеша и HTTP API — только здесь.
3. Изменение JSON-контракта требует отдельной версии API и одновременной проверки обеих сторон.
4. HAR, токены, cookies, персональные данные и рабочие конфиги не коммитить.
