# Архитектура многозонного FR24-сервера

## Поток данных

```text
ESP32 #1 ─┐
ESP32 #2 ─┼─ HTTP /v2/lat/... ─> AreaRegistry (5 s batch)
ESP32 #N ─┘                         │
                                   v
                         Merge overlapping circles
                           │                 │
                      Area A             Area B
                           │                 │
                           v                 v
                    FR24 LiveFeed      FR24 LiveFeed
                           │                 │
                           └──────┬──────────┘
                                  v
                         Shared AircraftCache
                                  │
                    per-device distance filtering
                                  │
                           JSON response
```

## Обработка запросов

- Каждый HTTP-запрос регистрирует координаты и радиус.
- Одинаковые зоны дедуплицируются по округлённым координатам и радиусу.
- После первого запроса запускается фиксированное окно сбора 5 секунд.
- Реестр хранит активные зоны 35 секунд, чтобы кратковременная задержка устройства не удаляла его зону сразу.
- Пересекающиеся круги объединяются в охватывающий круг; непересекающиеся остаются отдельными.
- Коллектор выполняет один LiveFeed-запрос на каждую объединённую область за цикл.
- Все полученные самолёты обновляют общий кеш. API фильтрует общий кеш отдельно для координат каждого клиента.

## Кеши

1. **AircraftCache** — общий набор последних позиций самолётов (существующая логика, ограничение возраста 120 секунд).
2. **HTTP response cache** — одинаковый запрос координат/радиуса повторно использует JSON-ответ в течение 5 секунд; максимум 512 ключей.
3. **AreaRegistry** — краткосрочная регистрация зон, не является хранилищем самолётов.

## Ограничения и дальнейшие улучшения

- Объединённый круг может захватить дополнительную территорию между исходными кругами; это компромисс для прямоугольного FR24-запроса.
- Очень крупная объединённая зона может быть неэффективна или превысить ограничения источника; требуется лимит и разбиение на этапе 2.
- При нескольких удалённых группах будет несколько upstream-запросов. 100 ESP32 не означают один запрос FR24.
- Коллектор ограничивает число областей за цикл (`max_areas_per_cycle`, по умолчанию 20); остаток обслуживается по кругу, чтобы удалённые зоны не голодали.
- Между запросами к FR24 выдерживается минимальная пауза (`upstream_interval_seconds`, по умолчанию 250 мс).
- Временные HTTP/сетевые ошибки повторяются с экспоненциальной задержкой; 401/403 не повторяются и останавливают сборщик.
- Таймаут и количество повторов задаются в `radar_config.json`.
- HAR является секретом сессии и должен храниться только локально.
- Вблизи линии перемены дат текущая функция построения bbox может отклонить область. Не размещайте такие зоны без отдельного теста.

## Планирование upstream-запросов

`AreaScheduler` хранит следующий ключ зоны, а не только индекс списка. Это сохраняет точку Round-Robin при изменении порядка активных областей. Если следующая зона истекла, планировщик начинает с первой доступной.

`UpstreamClient` централизует интервал между всеми попытками, таймаут и повторы. Повторяются сетевые ошибки, HTTP 429 и HTTP 5xx; прочие HTTP 4xx не повторяются. HTTP 401/403 немедленно останавливают сборщик.

Для 100 непересекающихся активных зон при лимите 20 требуется не менее пяти проходов планировщика, чтобы обслужить каждую зону один раз. Это гарантия очередности, а не временная гарантия: upstream-запросы могут занимать до настроенного таймаута и повторяться. При 100 удалённых зонах свежесть будет хуже, чем при 100 устройствах, сгруппированных в небольшое число пересекающихся областей.


## Декодирование расширенных данных LiveFeed

Коллектор декодирует не только обычные записи `Feed` (поле 1 ответа), но и `selected_feeds` (поле 3). Последние могут содержать `ExtraFlightInfo`, отсутствующий в общей записи того же самолёта. Оба потока объединяются в кеше по внутреннему ID FR24; значения обновляются только при наличии ненулевого значения в сообщении.

Поля Feed 4/5/6/8/10 интерпретируются как track, altitude_ft, speed_kt, status enum и on_ground соответственно. ICAO HEX формируется только из 24-битного ICAO address в ExtraFlightInfo; внутренний FR24 ID никогда не используется как ICAO. Коды enum остаются числовыми, если для них нет проверенной таблицы текстовых подписей.
