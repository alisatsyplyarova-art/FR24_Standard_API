# FR24 Standard API — техническое руководство и инструкция для разработчика

> Документ описывает текущую реализацию ветки `feature/esp32-altitude-speed` репозитория [FR24_Standard_API](https://github.com/alisatsyplyarova-art/FR24_Standard_API) и интеграцию с прошивкой [Flight Radar-D & Clock 1.1.127](https://github.com/alisatsyplyarova-art/flight-radar-d-clock/tree/feature/fr24-standard-altitude-speed-1.1.127).
>
> **Статус:** рабочая документация к текущему коду, а не утверждение, что каждое необязательное поле уже подтверждено на реальном потоке FR24. Протокольные номера и типы вложенных полей необходимо сверять с реальными обезличенными захватами и официально/независимо подтверждённой схемой. Неизвестные и недоступные поля должны оставаться отсутствующими или `null`.

## 1. Что это за система

Проект состоит из двух независимых программ:

1. **FR24 Standard API (Python, сервер в локальной сети).** Получает поток FR24 LiveFeed, разбирает транспорт gRPC-Web и protobuf, хранит последние позиции самолётов в оперативной памяти и предоставляет HTTP API.
2. **Flight Radar-D & Clock (ESP32, прошивка 1.1.127).** Запрашивает локальный сервер, фильтрует полученные самолёты, преобразует единицы измерения и отображает воздушную обстановку на дисплее.

Сервер нужен как промежуточный адаптер: ESP32 не должен самостоятельно разбирать внутренний бинарный протокол FR24 и использовать HAR/сессионные данные.

### Поток данных

```text
Браузер с открытым Flightradar24
        |
        | HAR: шаблон POST LiveFeed + разрешённые заголовки
        v
FR24 Standard API (Python)
        |
        | HTTPS POST data-feed.flightradar24.com/.../LiveFeed
        v
FR24 LiveFeed
        |
        | gRPC-Web frames
        v
protobuf FeedResponse
        |
        +--> Feed (позиция, скорость, высота, метаданные)
        |       |
        |       +--> ExtraFlightInfo (вложенные сведения о рейсе)
        |       +--> PositionBuffer (история координат)
        |
        v
AircraftCache (последние позиции и сведения)
        |
        +--> GET /health
        +--> GET /aircraft
        +--> GET /v2/lat/{lat}/lon/{lon}/dist/{nm}
                         ^
                         |
                  ESP32 1.1.127
                         |
              экран радара / часы
```

## 3. Что делает сервер

Текущие основные функции:

- периодически (обычно каждые 10 секунд) опрашивает FR24 LiveFeed;
- использует тело запроса и разрешённые заголовки из собственного HAR;
- меняет географическую область следующего запроса в зависимости от последнего запроса ESP32;
- разбирает gRPC-Web кадры;
- декодирует protobuf-сообщения;
- восстанавливает текущие координаты и историю позиций;
- хранит последние позиции в ограниченном оперативном кэше;
- удаляет устаревшие самолёты;
- отдаёт JSON через HTTP на порту 8765.

Сервер не является официальным публичным API FR24. Его работа зависит от доступности LiveFeed и действительности пользовательского HAR/сессии.

### Роли основных модулей

**main.py**

1. Читает `radar_config.json`.
2. Находит в HAR POST-запрос к LiveFeed.
3. Извлекает шаблон protobuf-тела запроса и только разрешённые заголовки.
4. Проверяет структуру шаблона, прежде чем менять координаты области.
5. Запускает HTTP API.
6. Каждые 10 секунд отправляет POST-запрос к FR24.
7. Передаёт ответ в декодер и обновляет кэш.

Если FR24 возвращает HTTP 401/403, сборщик прекращает работу. Ошибки отдельных циклов записываются в журнал.

**grpc_web.py**

У gRPC-Web кадра пятибайтовый заголовок: один байт флагов и четыре байта длины в big-endian. Далее идёт payload указанной длины. Функция `decode_grpc_web_body()` последовательно выделяет кадры, различает data/trailer и отмечает сжатые кадры. Текущий цикл пропускает сжатые data-кадры, а не пытается ошибочно интерпретировать их как protobuf.

**protobuf_parser.py**

Поддерживает основные wire types protobuf:

- 0 — VARINT;
- 1 — 64-bit;
- 2 — LEN (строка, байтовый блок или вложенное сообщение);
- 5 — 32-bit.

Парсер сохраняет номер поля, wire type, исходные байты и смещение. Это важно: неизвестные поля нельзя терять при исследовании новых версий протокола.

**feed_decoder.py**

Преобразует сырые поля в объекты `FeedResponse` и `Feed`. В нём находятся функции для разбора истории позиций, вычисления координат исторических точек и извлечения известных вложенных полей.

**aircraft_cache.py**

Хранит самолёты по внутреннему идентификатору FR24. Для одного самолёта хранится ограниченная история точек. Настройки по умолчанию: не более 120 точек на самолёт и не более 120 секунд без обновления позиции.

**api_server.py**

Предоставляет GET-маршруты `/health`, `/aircraft`, `/api/radar`, `/protobuf/latest` и `/v2/lat/...`. Для ESP32 выбирает самолёты в заданном радиусе, сортирует по расстоянию и возвращает JSON с декодированными и исходными protobuf-данными.

## 5. Транспорт и protobuf: как читать данные

Важно различать три уровня:

1. **HTTP** — запрос/ответ между сервером и FR24.
2. **gRPC-Web** — обрамление бинарного тела в кадры.
3. **protobuf** — структура сообщений внутри data-кадров.

Нельзя искать JSON с координатами внутри исходного ответа FR24: полезная нагрузка бинарная.

### Wire types

| Wire type | Как хранится значение | Как обрабатывать |
|---|---|---|
| 0 / VARINT | целое переменной длины | `first_varint()` |
| 1 / 64-bit | 8 байт | отдельная интерпретация |
| 2 / LEN | длина + байты | строка, байтовый блок или вложенный protobuf |
| 5 / 32-bit | 4 байта | например float32 через little-endian |

**Ключевой принцип:** wire type сам по себе не сообщает смысл значения. Например, VARINT может быть счётчиком, enum, bool или signed int64. Нужна схема конкретного сообщения.

### Основное сообщение Feed

Текущая реализация декодирует следующие поля корневого сообщения Feed:

| Поле protobuf | Текущий атрибут Python | Предполагаемый смысл | Замечание |
|---:|---|---|---|
| 1 | `field_1` | внутренний FR24 ID | Это НЕ ICAO HEX |
| 2 | `field_2` | latitude | читается как fixed32 float |
| 3 | `field_3` | longitude | читается как fixed32 float |
| 4 | `field_4` | track | int32, истинный путевой угол от севера по часовой стрелке, градусы |
| 5 | `field_5` | altitude_ft | int32, барометрическая высота, футы |
| 6 | `field_6` | speed_kt | int32, путевая скорость, узлы |
| 7 | `field_7` | icon | enum Icon; код типа значка |
| 8 | `field_8` | status | enum Status |
| 9 | `field_9` | timestamp | int32, Unix timestamp в секундах |
| 10 | `field_10` | on_ground | bool |
| 11 | `field_11` | callsign | string |
| 12 | `field_12` | source | enum DataSource |
| 13 | `ExtraFlightInfo` | дополнительные сведения | вложенное LEN-сообщение |
| 14 | `PositionBuffer` | история координат | вложенное LEN-сообщение |
| 15 | `field_15` | timestamp_ms | uint64, Unix timestamp в миллисекундах |

Таблица сверена с независимым открытым описанием protobuf в igolaizola/fr24, файлом pkg/proto/_common.proto. Поля 9 и 15 — разные временные представления, их нельзя взаимозаменять. Сверка схемы не гарантирует заполненность поля в каждом конкретном ответе.

### FeedResponse — контейнер ответа LiveFeed

По независимой схеме pkg/proto/_live_feed.proto структура ответа содержит:

| Поле | Тип | Значение | Обработка в нашем сервере |
|---:|---|---|---|
| 1 | repeated Flight | обычный список самолётов | декодируется и поступает в кэш |
| 2 | Stats | статистика по источникам | декодируется в FeedResponse.stats |
| 3 | repeated Flight | отдельно выбранные самолёты | декодируется и также поступает в кэш |
| 4 | uint64 | server_time_ms, время сервера в миллисекундах | сохраняется в FeedResponse.server_time_ms |

Поле 3 важно: выбранный самолёт может содержать ExtraFlightInfo, которого нет у записи того же самолёта в общем списке. Поэтому сборщик объединяет обычные и выбранные записи по внутреннему FR24 ID. Это не означает, что все дополнительные поля доступны для любого самолёта.

### Enum в Feed

Схема определяет следующие enum:

- DataSource: ADSB=0, MLAT=1, FLARM=2, FAA=3, ESTIMATED=4, SATELLITE=5, OTHER_DATA_SOURCE=6, UAT=7, SPIDERTRACKS=8, AUS=9.
- Status: NORMAL=0, BACKGROUND=1, EMERGENCY=2, NOT_AVAILABLE=3, LIVE=4.
- Icon: числовые коды типов самолётов/значков, от B738=0 до CONC=30 в опубликованной версии схемы.

REST API сохраняет числовые коды icon, status и source, не подменяя их догадочными текстовыми названиями. Полная таблица Icon находится в исходном .proto.

### История координат — PositionBuffer

Текущий декодер обрабатывает корневое поле 14 как вложенное сообщение. Внутри него повторяющееся поле 1 читается как отдельный сэмпл:

| Поле сэмпла | Текущее использование |
|---:|---|
| 1 | delta latitude |
| 2 | delta longitude |
| 3 | delta time |

Координаты рассчитываются относительно текущей позиции:

- `latitude = current_latitude - signed_delta_lat * 1e-5`;
- `longitude = current_longitude - signed_delta_lon * 1e-5`;
- `timestamp = current_timestamp_ms - delta_time`.

В текущем коде delta latitude/longitude интерпретируются как signed int64 в дополнительном коде, а не ZigZag. Это основано на проверке проекта: 90 совпадений с контрольными координатами с ошибкой не более 1e-5 градуса. Не меняй эту интерпретацию без повторной проверки на тестовых данных.

Точки сортируются по времени. Текущая позиция добавляется как последняя точка. Неполные исторические сэмплы не используются для построения траектории, но остаются доступными в диагностической структуре.

### ExtraFlightInfo — дополнительные сведения

Корневое поле 13 разбирается как вложенное protobuf-сообщение. Текущая реализация пытается извлечь следующие атрибуты:

| Поле ExtraFlightInfo | Имя в JSON/API | Смысл | Статус |
|---:|---|---|---|
| 1 | `flight_number` | номер рейса | требует проверки wire type и примеров |
| 2 | `registration` | регистрация борта | требует проверки |
| 3 | `route` | вложенный маршрут | вложенная структура |
| 4 | `aircraft_type` | тип самолёта | требует проверки |
| 5 | `squawk` | код ответчика | может отсутствовать |
| 6 | `vertical_speed_fpm` | вертикальная скорость, ft/min | может отсутствовать; signed decode |
| 7 | `aircraft_age` | возраст/год выпуска в представлении FR24 | формат проверить |
| 8 | `country_of_reg` | код страны регистрации | код, не обязательно текстовое название |
| 9 | `schedule` | вложенное расписание | вложенная структура |
| 10 | `logo_id` | идентификатор логотипа | не изображение |
| 11 | `airspace` | атрибут воздушного пространства | enum/код проверить |
| 12 | `ems_info` | вложенная телеметрия EMSInfo | вложенная структура |
| 13 | `ems_availability` | отдельное сообщение EMSAvailability | вложенная структура с bool-флагами |
| 14 | `icao_address` | 24-битный ICAO address | если поле действительно присутствует |
| 15 | `operated_by_id` | ID оператора | код, не название |
| 16 | `squawk_availability` | флаг доступности squawk | bool |
| 17 | `vspeed_availability` | флаг доступности вертикальной скорости | bool |
| 18 | `airspace_availability` | флаг доступности airspace | bool |
| 19 | `airspace_id` | ID/строковый атрибут airspace | проверить тип |

Текущий код также пробует прочитать в Route поля 1–3 как origin, destination и diverted_to. В Schedule пробует прочитать поля 1–7 как STD, ETD, ATD, STA, ETA, ATA и progress_pct. В EMS извлекает поля 1–13 (QNH, AMCP, AFMS, OAT, IAS, TAS, Mach, GPS altitude и другие показатели). Отдельное EMSAvailability в поле 13 извлекает 13 bool-флагов доступности: qnh, amcp, afms, oat, ias, tas, mach, agps, agpsdiff, apflags, wind_dir, wind_speed и rs. Эти флаги не являются самими измерениями.

**Это кандидаты декодирования, а не гарантия присутствия или правильности каждого значения.** До подтверждения реальным захватом не использовать их для критических решений и не трактовать кодовые поля как человекочитаемые подписи.

### ICAO HEX и внутренний ID FR24

Это разные идентификаторы:

- `fr24_id` — внутренний ключ FR24, используется сервером для объединения обновлений одного борта;
- `icao_address` — числовой 24-битный ICAO address, если FR24 передал его в ExtraFlightInfo;
- `icao_hex` — строковое представление 24-битного адреса в шестнадцатеричном виде, например шесть hex-символов.

Запрещено преобразовывать `fr24_id` в ICAO HEX или выдавать его за ICAO. Если ICAO отсутствует, идентификатор ICAO должен оставаться пустым/неизвестным.

## 6. Динамическая область радара

Сервер использует `radar_config.json` как начальную область. После запроса ESP32 область обновляется через `set_active_area()` и применяется к следующему циклу опроса FR24.

Последовательность:

1. До первого обращения ESP32 используется `latitude`, `longitude`, `radius_km` из конфигурации.
2. ESP32 вызывает `/v2/lat/{latitude}/lon/{longitude}/dist/{distance}`.
3. Параметр `distance` — морские мили (NM).
4. Сервер переводит NM в километры и сохраняет активную область.
5. Следующий запрос к FR24 формируется для нового центра и радиуса.
6. Ответ ESP32 дополнительно фильтруется по точному расстоянию до каждой текущей позиции.

Ограничение: используется одна общая активная область. Если одновременно подключены несколько радаров с разными центрами, действует область последнего запроса.

При формировании прямоугольной области запроса сервер проверяет географические границы и не должен молча создавать некорректный шаблон. Текущий код явно отклоняет область, пересекающую линию перемены дат.

## 7. HTTP API

Сервер слушает порт **8765**. В `main.py` используется `API_HOST = "0.0.0.0"`, то есть сервер доступен на сетевых интерфейсах машины. Разрешай доступ к порту только из доверенной локальной сети/межсетевым экраном.

### GET /health

Проверка работоспособности.

Пример структуры ответа:

```json
{
  "status": "ok",
  "aircraft": 12,
  "active_area": {
    "latitude": 54.91,
    "longitude": 82.33,
    "radius_km": 100,
    "radius_nm": 53.996
  },
  "source_stats": [
    {"source": 0, "count": 10},
    {"source": 1, "count": 2}
  ],
  "feed_server_time_ms": 1790000000000,
  "now": 1790000001000
}
```

Числа выше иллюстративные, не являются результатом реального запроса. source_stats — последняя статистика LiveFeed по enum DataSource. feed_server_time_ms — время сервера FR24 из FeedResponse.field_4. feed_response_frames — количество data-кадров FeedResponse, сохранённых для диагностики. now — локальное время формирования /health.

### GET /protobuf/latest

Возвращает исходные поля последнего успешно разобранного FeedResponse по кадрам: `frames`, `count`, `feed_server_time_ms` и `timestamp`. Вложенные LEN-поля содержат исходные байты и, когда возможно, `nested_candidate` с wire-полями вложенного protobuf.

### GET /aircraft

Возвращает полный снимок кэша, число бортов и время формирования ответа. Для каждого борта доступны текущая позиция, массив `points`, число точек, время последнего обновления, распознанные метаданные и исходные protobuf-сообщения в `protobuf_messages`.

### GET /api/radar

Совместимый плоский список самолётов. Возвращает `aircraft`, `count` и `timestamp`. Элементы списка содержат `fr24_id`, `lat`, `lon`, `seen`, `seen_pos`, все доступные декодированные атрибуты, историю `points` и `protobuf_messages`. Для совместимости с прошивкой дополнительно выдаются `flight` (если есть callsign), `track` и `hex` (только если реально получен `icao_hex`).

### GET /v2/lat/{latitude}/lon/{longitude}/dist/{distance}

Основной маршрут для ESP32.

Параметры:

- `latitude`: широта центра, диапазон -90…90;
- `longitude`: долгота центра, диапазон -180…180;
- `distance`: радиус в NM, больше 0 и не более 500.

Ответ имеет форму:

```json
{
  "ac": [
    {
      "fr24_id": "FR24_INTERNAL_ID",
      "lat": 54.91,
      "lon": 82.33,
      "seen": 1.2,
      "seen_pos": 1.2,
      "flight": "CALLSIGN",
      "track": 270,
      "altitude_ft": 32000,
      "speed_kt": 450,
      "icao_hex": "ABC123",
      "registration": "REGISTRATION",
      "aircraft_type": "TYPE"
    }
  ],
  "msg": "No error",
  "now": 1790000000000,
  "total": 1,
  "ctime": 1790000000000,
  "ptime": 0
}
```

Все значения в примере вымышлены. В реальном ответе необязательные поля могут отсутствовать. Не считай пример гарантированной схемой фактического ответа.

Основные поля:

| JSON | Назначение |
|---|---|
| `fr24_id` | внутренний идентификатор FR24 |
| `lat`, `lon` | текущие координаты |
| `seen` | возраст последнего обновления записи |
| `seen_pos` | возраст позиции |
| `timestamp_s` | исходное Feed.field_9, Unix seconds, если присутствует |
| `timestamp_ms` | исходное Feed.field_15, Unix milliseconds |
| `flight` | callsign из Feed.field_11 |
| `track` | track из Feed.field_4; при отсутствии может использоваться вычисленный heading |
| `altitude_ft` | высота в футах |
| `speed_kt` | скорость в узлах |
| `icao_hex` | ICAO HEX, если декодирован |
| прочие метаданные | поля ExtraFlightInfo и корневого Feed, если доступны |

Самолёты сортируются по расстоянию от запрошенного центра. Внутреннее поле расстояния удаляется перед отправкой.

### Без потерь: исходные protobuf-поля

Декодированные поля нужны для обычной работы радара, но они не заменяют исходное protobuf-сообщение. Сервер дополнительно сохраняет каждое вхождение поля, в том числе неизвестные номера и повторяющиеся поля.

В `protobuf_messages.feed.message.fields[]` и `protobuf_messages.selected_feed.message.fields[]` передаются:

| JSON-поле | Значение |
|---|---|
| `number` | номер protobuf-поля |
| `wire_type` / `wire_type_name` | исходный wire type и его название |
| `offset` | смещение поля в исходном сообщении |
| `value_uint64` | числовое значение только для VARINT |
| `length` | размер содержимого только для LEN |
| `raw_value_base64` / `raw_value_hex` | исходные байты значения |
| `raw_field_base64` / `raw_field_hex` | полная исходная кодировка поля, включая ключ и длину |

Для fixed32/fixed64 семантическое значение намеренно не угадывается: передаются исходные байты. Для LEN передаётся полное содержимое; дополнительно декодер пробует разобрать его как вложенный protobuf и, если wire format корректен, добавляет `nested_candidate` с номерами и wire type внутренних полей. Это именно кандидат разбора, а не утверждение о семантике сообщения. Даже при неудаче вложенного разбора исходные байты сохраняются. Рекурсивный анализ ограничен глубиной 8 и 10 000 полями на экспорт. Исходные поля контейнера FeedResponse по кадрам доступны через `GET /protobuf/latest`; `/health` остаётся компактным и возвращает только число сохранённых кадров.

Экспорт не означает, что каждое поле уже семантически расшифровано. Известные поля доступны отдельно в обычных ключах JSON. Неизвестные значения нельзя выдавать за ICAO, высоту, скорость или другие атрибуты без подтверждения схемой.

### Важное замечание об ICAO в текущей интеграции

В текущем исходнике ESP32 1.1.127 JSON-фильтр запрашивает ключ `hex`, тогда как серверный API в текущей реализации передаёт поле `icao_hex`. Это несоответствие имён нужно устранить отдельным согласованным изменением: либо сервер добавляет совместимый alias `hex`, либо прошивка читает `icao_hex`, либо оба варианта поддерживаются для обратной совместимости. До исправления нельзя считать, что ICAO HEX уже проходит весь путь до дисплея.

## 8. Единицы измерения и преобразования

| Поле FR24 | Единица FR24 | Единица прошивки | Преобразование |
|---|---|---|---|
| altitude_ft | футы | метры | `ft * 0.3048` |
| speed_kt | узлы | м/с | `kt * 0.514444` |
| vertical_speed_fpm | футы/мин | м/с | `fpm * 0.00508` |
| radius_nm | морские мили | километры | `NM * 1.852` |

При округлении радиуса используется `ceil(km / 1.852)`, чтобы округление не уменьшало запрошенную область.

Вертикальную скорость нельзя интерпретировать без проверки знака: обычно положительное значение означает набор высоты, отрицательное — снижение, но это должно быть подтверждено для конкретного источника и декодера.

## 10. Журналы и диагностика

Основной журнал:

`logs/collector.log`

В нём полезны:

- номер запроса;
- HTTP status;
- размер ответа;
- активный центр и радиус;
- число декодированных Feed;
- число самолётов в кэше;
- предупреждения декодера.

Для анализа бинарного потока в конфигурации предусмотрена опция `save_captures`. Если она включена, сырые ответы сохраняются в `captures/` с временной меткой.

Сырые захваты могут содержать данные, которые не следует публиковать. Перед передачей разработчику нужно удалить секреты и проверить содержимое. Лучше сделать обезличенную копию protobuf payload без HAR, cookies, заголовков, device ID и токенов.

### Диагностика по слоям

1. **Нет ответа FR24:** проверить сеть, DNS, время системы и актуальность HAR.
2. **HTTP 401/403:** вероятна недействительная/недостаточная сессия; не пытаться обходить ограничения доступа.
3. **HTTP 200, но 0 Feed:** проверить gRPC-Web флаги, длины кадров и protobuf payload.
4. **Feed есть, координат нет:** проверить поля 2/3 и их wire type.
5. **Координаты есть, но самолёт исчезает:** проверить timestamp, единицы времени и max_age.
6. **Самолёты есть в /aircraft, но нет в /v2:** проверить центр, радиус в NM и фильтр расстояния.
7. **Метаданные пусты:** проверить наличие поля 13 в исходном Feed и формат вложенного сообщения.
8. **ICAO пустой на ESP32:** проверить согласование ключей `icao_hex` и `hex` и не использовать FR24 ID как замену.

## 11. Ограничения и известные вопросы текущего состояния

Перед расширением функциональности необходимо учитывать:

1. **Не все поля гарантированы.** Набор данных может зависеть от типа потока, авторизации, выбранного самолёта и доступности FR24.
2. **Схема вложенных сообщений требует тестовых подтверждений.** В частности, Route, Schedule, EMS и отдельные поля ExtraFlightInfo нельзя объявлять достоверными только потому, что декодер умеет прочитать их как protobuf.
3. **Enum пока не преобразованы в справочники.** `status`, `source`, `airspace`, `icon` могут быть числовыми кодами.
4. **Часть значений может быть signed.** Нельзя применять `int64_decode` ко всем VARINT подряд; нужно подтвердить тип конкретного поля.
5. **Поле ICAO требует отдельного теста.** Число должно быть в диапазоне 0…0xFFFFFF и подтверждено сравнением с известным ICAO HEX.
6. **Несовпадение `hex` / `icao_hex`.** Нужно согласовать контракт между сервером и прошивкой.
7. **Один активный радар.** Несколько ESP32 с разными областями сейчас не имеют независимых потоков.
8. **Сжатые gRPC-Web data frames пропускаются.** Если FR24 начнёт их присылать, потребуется согласованная реализация декомпрессии.
9. **Кэш оперативный.** После перезапуска сервера история очищается.
10. **Нет подтверждения реальной эксплуатации только по факту коммита.** Нужны тесты, компиляция/запуск и проверка живого ответа.

## 12. Как правильно добавлять новые поля

Для каждого нового поля следуй этому процессу:

1. Получить обезличенный реальный protobuf Feed, где поле присутствует.
2. Определить, на каком уровне оно находится: Feed, ExtraFlightInfo, Route, Schedule, EMS или PositionBuffer.
3. Определить protobuf field number и wire type.
4. Установить тип значения: string, uint, signed int64, bool, enum, float или вложенное сообщение.
5. Сверить значение с независимым источником/интерфейсом FR24, если возможно.
6. Добавить атрибут в `model.py`.
7. Реализовать безопасное декодирование в `feed_decoder.py`.
8. Сохранить значение в `aircraft_cache.py`.
9. Опубликовать поле в нужном HTTP endpoint в `api_server.py`.
10. Добавить тест на бинарный пример, тест отсутствующего поля и тест неправильного wire type.
11. Проверить обратную совместимость: отсутствие поля не должно ломать весь Feed.
12. Обновить этот документ и пример JSON только после подтверждения.

Нельзя:
- угадывать номера полей;
- трактовать все VARINT как signed;
- трактовать любой LEN как UTF-8 строку;
- использовать внутренний FR24 ID как ICAO;
- выдумывать данные, если поле отсутствует;
- удалять неизвестные поля из диагностического вывода без причины;
- отправлять HAR/токены/куки в Git.

**Главное правило проекта:** сначала докажи структуру и значение поля на реальном обезличенном образце, затем добавляй его в декодер, кэш и API. Не путай внутренний ID FR24 с ICAO, не публикуй HAR и не заявляй о проверке, которую фактически не выполнял.


## 14. Независимые реализации и источники схемы

При аудите сравнивались только независимые проекты и открытые реализации, не официальный FR24 API:

- igolaizola/fr24 — https://github.com/igolaizola/fr24 — Go-клиент/CLI, использует gRPC-Web и содержит protobuf-схемы в pkg/proto. Для сверки использованы _common.proto и _live_feed.proto. Это клиент и CLI, а не готовый универсальный REST-сервер.
- AlexandrErohin/home-assistant-flightradar24 — https://github.com/AlexandrErohin/home-assistant-flightradar24 — интеграция Home Assistant, использует отдельную библиотеку FlightRadarAPI и HTTP-источники; полезна как пример нормализации атрибутов, трекинга, истории и обработки ограничений, но не является реализацией нашего gRPC-Web декодера.
- t7spotter/liveflights — https://github.com/t7spotter/liveflights — Flask-приложение, которое предоставляет REST/JSON поверх нескольких upstream HTTP endpoints FR24. Это пример REST-обёртки, но не сервер для приёма нашего LiveFeed protobuf потока.
- grega/flight-finder — https://github.com/grega/flight-finder — Flask API для маломощных Wi-Fi устройств: /health, /closest-flight и /flights-in-radius; ответ содержит позицию, высоту, скорость, вертикальную скорость, регистрацию, ICAO 24-bit и маршрут. Получает данные через библиотеку FlightRadarAPI, а не через наш protobuf LiveFeed. По назначению ближе всего к нашему ESP32-клиенту.
- huntrw6/airspace — https://github.com/huntrw6/airspace — self-hosted Docker PWA с картой, профилями зон и уведомлениями; backend опрашивает FR24 HTTP JSON feed и clickhandler, ограничивает число detail-запросов и учитывает HTTP 429. Имеет собственные API маршруты для интерфейса, но это полноценное приложение, не чистый адаптер protobuf.
- Snr1s3/FlightsASL — https://github.com/Snr1s3/FlightsASL — FastAPI + PostgreSQL, хранит аэропорты и расписания рейсов, предоставляет Swagger/OpenAPI и API для поиска/сохранения расписаний. Использует библиотеку-клиент FR24; не потоковый LiveFeed сервер.
- mitchtech/flight-exporter — https://github.com/mitchtech/flight-exporter — Docker Prometheus exporter, отдаёт метрики /metrics по самолётам в заданном радиусе; не JSON REST API общего назначения.

В текущем проекте применены подтверждённые protobuf-структуры и идеи обработки выбранных рейсов/дополнительных атрибутов. Код чужих проектов целиком не копировался. Схема из открытого репозитория — независимое техническое описание, а не официальная спецификация FR24; при изменениях протокола её нужно повторно сверять с живыми обезличенными payload.
